Nobody can re-check that by hand on every runtime upgrade.

Between Portaldot’s docs and its runtime

Plumblinethe middleware

plumb · diff · check · canary
through the SDK Portaldot’s docs point to, substrate-interface 1.8.1. The canary uses compose_call · create_signed_extrinsic · submit_extrinsic · get_block · get_events; the read-only commands use RPC calls such as state_getMetadata.

Runtimeswhat actually runs

V3 testnet portaldot-v3 / 3002 · mainnet spec 1002, read-only: state_getMetadata · state_getRuntimeVersion · state_getStorageHash(:code)

Pinned to the real V3The v3 profile checks spec name portaldot-v3, genesis 0xd4f9acbc…5283bd and spec 3002, and fails loudly on a mismatch.
Re-run per upgradeThe spec 1002 baseline and the spec 3002 sheet come from the same commands; the next runtime is the next run.
Plumbline reads Portaldot's two live runtimes and its docs, plus the community V3 testnet guide, through the SDK the docs recommend. It is middleware in the literal sense: the layer between what Portaldot documents and what Portaldot runs; check runs a dApp's calls against V3 before anything is sent.
